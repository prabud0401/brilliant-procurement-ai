## Scope
1. **Extraction prompt** (live): value only, never the label or surrounding text; vendor name = the legal/trading name only, no TRN, address, phone or email; amounts as plain numbers (digits and a decimal point, no thousands separators, no currency); currency as a separate ISO code field; dates ISO `YYYY-MM-DD`; a field not present → null (do not infer VAT etc.). `source_text` keeps the exact text the value came from (labels allowed there). Keep the injection-defence wording and the strict json_schema.
2. **Deterministic value cleanup** (new module, e.g. `app/ai/normalize.py`), applied to every extraction result after the model (live and replay paths alike) and before storing/scoring: strip known leading labels (TRN, VAT No, Tax Registration Number, Number, No., Invoice/Quote/PO/DN No, Date, Currency, Terms, Due …, case-insensitive, with `:`/`#`/`-`); TRN = 15 digits extracted; vendor name cut at a TRN/address/phone/email marker or newline; amounts parsed to `Decimal` text (remove currency codes/symbols, thousands separators; keep sign); currency mapped to ISO (AED, "Dhs", "د.إ" → AED etc.); dates to ISO from common formats (DD/MM/YYYY UAE default, DD-Mon-YYYY, ISO); line-item quantities/prices the same. Record per field whether cleanup changed the value. Unit tests with the real examples above and edge cases (null, empty, negative, Arabic currency, unknown label kept).
3. **Confidence**: fields that cleanup had to change, fields whose cleaned value does not appear in the page text / `source_text`, failed parses (e.g. unparseable date/amount), and arithmetic mismatches (subtotal + VAT ≠ total, line sums) must score below the low-confidence threshold (`AI_LOW_CONFIDENCE_THRESHOLD`, 0.80) or at least clearly lower, so they are flagged for review. Keep high confidence only for values that match the document exactly. Unit tests.
4. **Q&A scoring (AIQ-06)**: fix the scorer so numbers in the expected answer are required and matched (normalise "10", "10.00", "10 units", "28,875.00", "AED 28,875"), and unit words like "units"/"pcs"/"items" are not required. Do not loosen anything else: a wrong number must still fail. Add scorer unit tests covering QA-12/13/14-style cases and a wrong-number case. Check the Q&A prompt/retrieval too; change them only if you find a real problem, and say what.
5. **Eval report detail**: for live runs include per-item failure details in report.json (failed header fields with expected vs got, failed Q&A with expected and answer text) so misses can be diagnosed without re-running.
6. Docs: short note in `docs/evaluation-report.md` method section on value cleanup and the Q&A scorer fix (no scores, they will be filled from the next live run).
