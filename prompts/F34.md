1. UUIDs still visible under document titles, on the document review ID line, as truncated match IDs, on linked quotes, and in the audit ENTITY column (`user a41c0c32…`). F31 allowed UUID as secondary text; now hide them and show human refs only.

## Scope

1. **Hide UUIDs in the UI.** Remove the secondary full-UUID line on the documents list, the `ID: {uuid}` line on document review (keep pages/size if useful; the human title already appears), truncated UUID suffixes on PR linked quotes and match headings, and the truncated match-id in the exception queue (link can stay, label should be a human invoice/vendor ref if the payload can provide it, otherwise a short "View match" link with no UUID text). Do not put the UUID in a visible tooltip either. Internal keys, routes and `data-testid` may still use the id.

2. **Audit ENTITY column.** API should return a human `entity_label` (or equivalent) for the list: users → email or display name; documents → vendor + document number (same rule as document titles); PRs/POs → their business number; matches → invoice number/vendor if known. If a label cannot be resolved, show the entity type and an em dash, not a sliced UUID. Hide `entity_id` from the table (and tooltips). Regenerate OpenAPI / `schema.d.ts` the way the repo already does.

3. **PO title.** Add `vendor_name` (from the linked vendor) to `POResponse` and populate it in `po_service`. Update `PODetail` heading to vendor · PO number as specified. Regenerated schema as above.

4. **Approval history on PR and PO detail.** Expose the existing `approval_steps` for a subject, including sequence, approver display name (Mariam / Khalid, not a UUID), department or role if cheap to include, status, `decided_at` (display in Asia/Dubai / GST), and comment if any. Show a compact history on both the PO and PR detail pages once the record has steps (e.g. Facilities PO-2026-1C8000: Mariam then Khalid). Do not change routing or who can approve. If a record has no steps, omit the section — do not invent names.

5. **Match invoice dropdown.** Only list invoices that are confirmed (or otherwise eligible to run a match) and not suspicious / not awaiting injection acknowledgement. INV-7001 must not appear. Prefer a query param on the documents list if one already exists or is a small additive filter; otherwise filter client-side on `status` + `suspicious` already on `DocumentSummary`. Keep the heading "Confirmed Invoice" honest.

6. Docs: one short line in `docs/release-notes.md`.
